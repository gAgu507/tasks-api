# Tasks API

REST API для списка задач на Go с PostgreSQL. У каждого пользователя свои задачи: регистрация, вход по паролю и доступ по JWT-токену.

Учебный проект. Что в нём есть:

- CRUD задач, работа с базой через `pgx`
- регистрация и вход, пароли хранятся в виде bcrypt-хешей, доступ по JWT
- изоляция данных: пользователь видит и меняет только свои задачи
- миграции базы (goose)
- тесты обработчиков и авторизации без базы данных
- запуск одной командой через Docker Compose

## Быстрый старт через Docker Compose

Go и PostgreSQL ставить не нужно, достаточно Docker (на Linux можно Podman).

1. Клонировать репозиторий и перейти в папку проекта:

   ```bash
   git clone https://github.com/gAgu507/tasks-api.git
   cd tasks-api
   ```

2. Создать файл настроек из шаблона:

   Linux / macOS / Git Bash:

   ```bash
   cp .env.example .env
   ```

   PowerShell:

   ```powershell
   copy .env.example .env
   ```

3. Открыть `.env` и заменить `JWT_SECRET` на длинную случайную строку (минимум 32 символа). Сгенерировать её можно так:

   ```bash
   openssl rand -hex 32
   ```

   Остальные значения можно оставить по умолчанию. Пароль базы для Compose лучше делать без спецсимволов.

4. Запустить всё одной командой:

   ```bash
   docker compose up --build
   ```

   На Linux с Podman: `podman compose up --build` (при необходимости `sudo dnf install podman-compose`).

   Compose поднимет три контейнера по порядку: PostgreSQL, затем миграции, затем сервер. Первый запуск дольше остальных, потому что скачиваются и собираются образы.

5. Проверить, что сервер отвечает:

   ```bash
   curl http://localhost:8080/
   ```

Полезные команды:

```bash
docker compose up -d --build   # запуск в фоне
docker compose logs -f app     # логи сервера
docker compose down            # остановить и удалить контейнеры (данные сохраняются)
docker compose down -v         # то же, плюс удалить данные базы
```

После изменений в миграциях запускай с `--build`, иначе контейнер миграций останется со старой версией.

База дополнительно доступна с твоего компьютера на порту `5433` (например, для `psql`). Данные хранятся в томе `pgdata` и переживают перезапуск контейнеров.

## Запуск без Docker

### Что нужно

- Go 1.22 или новее (в проекте используется маршрутизация по методам и параметры пути из стандартной библиотеки)
- PostgreSQL
- [goose](https://github.com/pressly/goose) версии 3.24.0 или новее для миграций (эта версия умеет читать настройки из `.env`):

  ```bash
  go install github.com/pressly/goose/v3/cmd/goose@latest
  ```

  Если команда `goose` не находится, добавь папку `go/bin` в `PATH` (`~/go/bin` на Linux, `%USERPROFILE%\go\bin` на Windows).

### Шаги

1. Клонировать репозиторий (см. выше) и создать базу данных:

   ```bash
   createdb tasks
   ```

   Если `createdb` не находит пользователя, создай базу через `psql` от имени суперпользователя (на Linux обычно `sudo -u postgres psql`).

2. Создать `.env` из шаблона, указать в нём `DATABASE_URL` и `GOOSE_DBSTRING` с адресом своей базы и задать `JWT_SECRET`.

3. Применить миграции:

   ```bash
   goose up
   ```

4. Запустить сервер:

   ```bash
   go run ./cmd/server
   ```

   По умолчанию сервер слушает `http://localhost:8080`.

## Настройки

Настройки читаются из файла `.env` в корне проекта. Шаблон лежит в `.env.example`. Сервер и `goose` нужно запускать из корня проекта, где лежит этот файл.

| Переменная | Для чего | По умолчанию | Описание |
|------------|----------|--------------|----------|
| `JWT_SECRET` | всегда | | Секрет для подписи токенов, минимум 32 символа (обязателен) |
| `POSTGRES_USER` | Compose | | Пользователь базы в контейнере |
| `POSTGRES_PASSWORD` | Compose | | Пароль пользователя |
| `POSTGRES_DB` | Compose | | Имя базы |
| `DATABASE_URL` | локальный запуск | | Строка подключения к PostgreSQL для сервера (обязательна) |
| `PORT` | локальный запуск | `8080` | Порт, на котором слушает сервер |
| `GOOSE_DRIVER` | локальные миграции | | Драйвер базы для goose, здесь `postgres` |
| `GOOSE_DBSTRING` | локальные миграции | | Строка подключения к базе для goose |
| `GOOSE_MIGRATION_DIR` | локальные миграции | | Папка с миграциями, здесь `./migrations` |

В Docker Compose адрес базы и порт собираются из переменных `POSTGRES_*` автоматически, поэтому `DATABASE_URL`, `PORT` и `GOOSE_*` нужны только для запуска без Docker.

Пример `.env`:

```
POSTGRES_USER=tasks_user
POSTGRES_PASSWORD=tasks_pass
POSTGRES_DB=tasks

DATABASE_URL=postgres://tasks_user:tasks_pass@localhost:5433/tasks
PORT=8080

GOOSE_DRIVER=postgres
GOOSE_DBSTRING=postgres://tasks_user:tasks_pass@localhost:5433/tasks
GOOSE_MIGRATION_DIR=./migrations

JWT_SECRET=замени-на-длинную-случайную-строку-из-32-и-более-символов
```

В этом примере локальный запуск подключается к базе из Compose на порт `5433`. Для обычного локального PostgreSQL укажи свои пользователя, пароль и порт `5432`.

Правила записи: без пробелов вокруг `=` и без кавычек. Спецсимволы в пароле базы (`@`, `:`, `/`, `#`) нужно кодировать в адресе, например `@` как `%40`.

Переменные, заданные в окружении (например, через `export` или в Docker), главнее значений из `.env`. Без `DATABASE_URL` или с коротким `JWT_SECRET` сервер сообщает об ошибке и завершает работу.

Файл `.env` содержит секреты и не попадает в Git. В репозитории лежит только шаблон `.env.example`.

## Авторизация

Все адреса задач требуют токен. Схема такая:

1. Зарегистрироваться: `POST /register` с email и паролем.
2. Войти: `POST /login`, в ответе придёт токен.
3. Передавать токен в заголовке каждого запроса:

   ```
   Authorization: Bearer <токен>
   ```

Подробности:

- Пароль от 8 до 72 символов. В базе хранится только bcrypt-хеш.
- Email приводится к нижнему регистру: `Anna@x.ru` и `anna@x.ru` это один аккаунт.
- Токен JWT подписан алгоритмом HS256 и действует 24 часа. После истечения нужно войти заново.
- Неверный пароль и несуществующий email дают одинаковый ответ `401`, чтобы нельзя было узнать, какие адреса зарегистрированы.
- Чужая задача возвращает `404`, как будто её не существует: так нельзя выяснить, есть ли задача с таким id у другого пользователя.
- Токен не шифруется, а только подписывается: его содержимое (id пользователя и срок действия) может прочитать любой, поэтому секретных данных в нём нет.

## Адреса

| Метод | Путь | Токен | Описание | Коды ответа |
|-------|------|-------|----------|-------------|
| GET | `/` | нет | Проверка, что сервер работает | 200 |
| POST | `/register` | нет | Регистрация | 201, 400, 409, 500 |
| POST | `/login` | нет | Вход, возвращает токен | 200, 400, 401, 500 |
| GET | `/me` | да | Id текущего пользователя | 200, 401 |
| GET | `/tasks` | да | Список своих задач | 200, 401, 500 |
| POST | `/tasks` | да | Создать задачу | 201, 400, 401, 500 |
| GET | `/tasks/{id}` | да | Получить свою задачу | 200, 400, 401, 404, 500 |
| PUT | `/tasks/{id}` | да | Заменить свою задачу целиком | 204, 400, 401, 404, 500 |
| DELETE | `/tasks/{id}` | да | Удалить свою задачу | 204, 400, 401, 404, 500 |

Значения кодов:

- `400`: неверный id, некорректный JSON, невалидные данные или слишком большое тело запроса (лимит 1 МБ)
- `401`: нет токена, токен неверный или истёк, либо неверные email или пароль при входе
- `404`: задачи с таким id нет или она принадлежит другому пользователю
- `409`: пользователь с таким email уже зарегистрирован
- `500`: внутренняя ошибка (например, недоступна база). Подробности пишутся в лог сервера и клиенту не отдаются

## Формат данных

Задача:

```json
{
  "id": 1,
  "title": "Купить хлеб",
  "description": "Ржаной, в магазине у дома",
  "completed": false
}
```

При создании обязателен только `title`. Поля `id` и `completed` назначает сервер, владельцем становится пользователь из токена.

`PUT` заменяет задачу целиком: если не передать `completed`, оно станет `false`.

Регистрация и вход принимают:

```json
{"email": "anna@example.com", "password": "secret123"}
```

Регистрация возвращает `{"id": 1, "email": "anna@example.com"}`, вход возвращает `{"token": "..."}`.

## Примеры

Готовый набор запросов лежит в [`docs/requests.http`](docs/requests.http). Он открывается в VS Code с расширением REST Client: над каждым запросом появляется ссылка Send Request, а токен подставляется автоматически из ответа запроса `login`.

Ниже те же сценарии через `curl`.

Регистрация и вход:

```bash
curl -X POST http://localhost:8080/register \
  -H "Content-Type: application/json" \
  -d '{"email": "anna@example.com", "password": "secret123"}'

curl -X POST http://localhost:8080/login \
  -H "Content-Type: application/json" \
  -d '{"email": "anna@example.com", "password": "secret123"}'
```

Из ответа на вход скопируй значение токена и подставь в следующие запросы:

```bash
TOKEN="вставь_сюда_токен"
```

Создать задачу:

```bash
curl -X POST http://localhost:8080/tasks \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"title": "Купить хлеб", "description": "Ржаной"}'
```

Получить список:

```bash
curl -H "Authorization: Bearer $TOKEN" http://localhost:8080/tasks
```

Отметить задачу выполненной:

```bash
curl -X PUT http://localhost:8080/tasks/1 \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"title": "Купить хлеб", "description": "Ржаной", "completed": true}'
```

Удалить задачу:

```bash
curl -X DELETE -H "Authorization: Bearer $TOKEN" http://localhost:8080/tasks/1
```

В PowerShell вместо `curl` пиши `curl.exe` и экранируй кавычки в JSON (`\"`), либо используй `Invoke-RestMethod`:

```powershell
$r = Invoke-RestMethod -Method Post -Uri http://localhost:8080/login `
  -ContentType "application/json" `
  -Body '{"email": "anna@example.com", "password": "secret123"}'

Invoke-RestMethod -Uri http://localhost:8080/tasks `
  -Headers @{ Authorization = "Bearer $($r.token)" }
```

## Миграции

Структура базы описана миграциями в папке `migrations/`: это пронумерованные SQL-файлы, каждый с одним изменением. Утилита goose помнит, какие из них уже применены, и накатывает только новые. В Docker Compose миграции применяются автоматически при каждом запуске.

При локальном запуске настройки подключения goose берёт из `.env`:

```bash
goose status   # что применено
goose up       # применить новые
goose down     # откатить последнюю
```

Новая миграция создаётся командой:

```bash
goose create название_изменения sql
```

Уже применённые миграции не редактируются: исправление оформляется новой миграцией.

Обрати внимание: миграция, добавляющая владельца задач (`user_id`), удаляет задачи, созданные до появления пользователей, потому что у них нет владельца.

## Тесты

```bash
go test ./...
```

Тесты не требуют базы данных и сети: вместо PostgreSQL подставляются фальшивые хранилища в памяти, которые реализуют интерфейсы `TaskStore` и `UserStore`. Проверяется:

- коды ответов и тела для всех адресов, включая ошибки хранилища (клиенту не должны утекать внутренние детали)
- регистрация и вход, в том числе дубликаты, неверный пароль и неизвестный email
- токены: корректный, истёкший, с чужой подписью, мусор
- middleware: заголовок отсутствует, неверная схема, плохой токен
- изоляция пользователей: чужие задачи не видны в списке, а `GET`, `PUT` и `DELETE` для них дают 404 и ничего не меняют
- лимит размера тела запроса

Подробный вывод по каждому случаю и отчёт о покрытии:

```bash
go test ./internal/handlers -v
go test -cover ./...
```

## Известные ограничения

Проект учебный, и в нём сознательно нет некоторых вещей, которые нужны в боевом сервисе:

- нет ограничения числа попыток входа, поэтому пароль можно перебирать
- токен нельзя отозвать до истечения срока (нет выхода из системы и обновления токена)
- сервер работает по обычному HTTP, без HTTPS: в реальной среде его ставят за обратным прокси с сертификатом
- ответ `409` при регистрации показывает, что email уже занят
- нет проверки подтверждения email и восстановления пароля
